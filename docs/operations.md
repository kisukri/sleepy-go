# デプロイと運用

以下のコマンドはすべてリポジトリのルートで実行します。すぐに試したい場合は [README](../README.md)、設定項目は [設定](configuration.md)、オリジナル版 Sleepy からの移行は [移行ガイド](migration.md) をご覧ください。

Sleepy Go は、paper デザインのトップページ、管理画面、文言エディター、`/api/…` API、そしてオリジナル版のクライアント向けの旧 API を提供します。HTML・CSS・JS・アイコンは実行ファイルに組み込まれているので、Python や Node、フロントエンドのビルドは要りません。

## ローカルで動かす

Go 1.25 以上が必要です。`go.mod` に `toolchain go1.27.3` を書いてあるので、古い Go を使っていてもこのバージョンが自動でダウンロードされ、標準ライブラリには最新のセキュリティ修正が入ります。SQLite には純粋な Go のドライバーを使っているので、`CGO_ENABLED=0` でビルドできます。

```sh
go mod download
go test -race ./...
go vet ./...
mkdir -p bin
go build -trimpath -ldflags='-s -w' -o bin/sleepy-go ./cmd/sleepy-go
```

起動する前に、空でないシークレットを設定します（強いシークレットを自分で作り、リポジトリにはコミットしないでください）。

```sh
export sleepy_main_secret='強いシークレットに置き換えてください'
export sleepy_page_name='あなたの名前'
./bin/sleepy-go
```

デフォルトでは `127.0.0.1:9010` でだけ待ち受けます。外部のインターフェースでも待ち受けるには `sleepy_main_host=0.0.0.0` を設定してください。データディレクトリはデフォルトで**作業ディレクトリの `data/`** で、`./bin/sleepy-go -data-dir /path/to/data` で変えられます。実行ファイルを別の場所に移したときに、空の新しいデータディレクトリで起動してしまわないよう気をつけてください。

設定ファイルを使う場合は、`configs/config.example.yaml` を `data/config.yaml` にコピーしてシークレットを書き込みます。優先順位は、デフォルト値 < `data/.env`・環境変数 < `data/config.yaml` < `data/config.toml` < `data/config.json` です。システムの環境変数は dotenv より優先され、`sleepy_` で始まる変数名は大文字・小文字を区別しません。設定ファイルは同じ名前の環境変数を上書きします。設定できるのは `main`、`page`、`status` と、3 つの内蔵モジュールの項目です。

設定ファイルで `main.https`、`main.ssl_cert`、`main.ssl_key` を指定すれば HTTPS も使えますが、ふつうはリバースプロキシの後ろに置けば十分です。プロキシでは Host ヘッダーをそのまま渡し、`X-Forwarded-Proto: https` を正しく設定し、SSE のバッファリングを無効にしてください。[`deploy/examples/`](../deploy/examples/) に Caddy と nginx の設定例があります。アプリに直接つなげるのは、信頼できるリバースプロキシだけにしてください。

## データ

データディレクトリ（デフォルトは `data/`）には、`data.db`（SQLite）、`text.json`（管理画面で編集した文言）、`session.key`（セッションの署名用）と、必要に応じて `config.*`、`.env`、`public/` が入ります。バックアップは、サービスを止めてからディレクトリごとコピーするだけです。

データベースは `main` と `device_status` の 2 つのテーブルを使い、オリジナル版 Sleepy と互換性があります。データベースにあるほかのテーブルは削除しません。デバイスの拡張情報 `fields` はそのまま保存し、日本語や絵文字も扱えます。`sqlite:///…` 形式で独自のパスを指定した場合、相対パスは作業ディレクトリの `instance/` を基準に解釈し、絶対パスはそのまま使います。対応しているのは SQLite だけです。オリジナル版からの移行は [移行ガイド](migration.md) をご覧ください。

## API とセッション

提供している API は次のとおりです。

- `/api/meta`、`/api/status/query`、`/api/status/list`、`/api/status/events`
- `/api/status/set`、`/api/device/set`、`/api/device/remove`、`/api/device/clear`、`/api/device/private`
- `/panel`、`/panel/login`、`/panel/auth`、`/panel/logout`、`/panel/verify`、`/panel/data`
- `/plugin/custom_text/text`（文言エディターのファイルは `/assets/<内容のハッシュ>/editor/…`）
- V4 互換を有効にしている場合は `/query`、`/events`、`/set`、`/status_list`、`/device/set`、`/device/remove`、`/device/clear`、`/device/private_mode`、`/save_data`

デバイスからのリクエストは、JSON の `secret`、`Authorization: Bearer …`、`Sleepy-Secret`、クエリパラメータのどれでも認証できます。互換クライアントの GET による書き込みも、**シークレットを明示的に付ければ**引き続き使えます。新しく作るクライアントでは POST とヘッダーを使ってください。

管理画面では、署名付きで有効期限（30 日）のある `sleepy-session` という HttpOnly Cookie を使います。共有シークレットそのものを Cookie に書くことはありません。署名鍵は共有シークレットとデータディレクトリの `session.key` から作られ、管理画面で「ログアウト」すると `session.key` を作り直すので、すべてのブラウザのセッションがすぐに無効になります。旧来の `sleepy-secret` Cookie は使えないので、ログインし直してください。管理画面の書き込みは POST で行い、Cookie で認証された GET の書き込みは拒否します。ブラウザからの書き込みは同一オリジンかどうかもチェックしています。HTTPS では Secure 属性付きの Cookie を使い、シークレットを変えると古いセッションは無効になります。

リクエストボディは 1 MiB までで、10 秒以内に送り終える必要があります（時間切れは 408。対象はリクエストボディだけなので、SSE の長時間接続には影響しません）。受け付けるのは JSON オブジェクト 1 つだけで、エラーには適切な HTTP ステータスコードを返します。デバイスの一部だけを更新するとき、`status: ""` を送れば前のタイトルを消せ、`using: false` もきちんと反映されます。省略した項目や null の項目は元の値を保ちます。初めて登録するときは `show_name` が必要です。範囲外の状態 ID には 400 を返します。

新旧どちらの SSE も、データが変わったという通知を受けて動き、変化がなければ 30 秒ごとにハートビートを送ります。切断されたら購読を解放し（HEAD リクエストにはヘッダーだけを返し、ストリームは開きません）、遅い接続には書き込みのタイムアウトがあります。同時接続は 256 本までです。再接続すると最新の状態をまとめて送り、`Last-Event-ID` による過去イベントの再送はしません。状態のスナップショットはトランザクションのコミット後に公開されるので、公開側の読み取りや待機中の長時間接続が SQLite を何度も読みにいくことはありません。最終更新時刻は、状態・デバイス・プライバシーモードが実際に変わったときだけ更新し、同じ状態やプライバシーモードを設定し直しても書き込みや配信はしません。デバイスからの送信は、毎回そのデバイスの時刻を更新します。データベースのどこかの行で `fields` が壊れていても、ログに記録して空として表示するだけで、起動やほかの書き込みには影響しません。

`data/public/` の公開ファイルは、作業ディレクトリの `public/` より優先されます。ディレクトリの外を指すパスやシンボリックリンクで外に出ることはできないので、本当に公開したいファイルだけを置いてください。組み込みのファイルは繰り返し・同時にアクセスされても問題ありません。

## できること・できないこと

- テーマは paper だけで、サードパーティのプラグインは読み込みません。
- `custom_text` と `v4_compatible` はデフォルトで有効で、`plugins_enabled` で切り替えられます。
- `auto_dead` は任意です。すべてのデバイスと全体の状態に一定時間動きがなければオフラインにし、デバイスから送信があれば状態 0 に戻します。プライバシーモードは判定に影響しません。古いデバイスが 1 台タイムアウトしただけでサイト全体がオフラインになる、ということはありません。
- **auto_dead はデフォルトで無効です**。古いクライアントは、ウィンドウが変わらないと送信しないことがあります。定期的にハートビートを送るクライアント（Go 版の `sleepy-client` など）を使ってから有効にしてください。クライアント側のマウス無操作の検出に問題があっても、サーバー側では直せません。
- バッテリーや再生中の曲の表示（解析と表示のオン/オフ）は paper のフロントエンドが担当しています。文言は、保存したあとトップページを再読み込みすると反映されます。
- 統計（metrics）機能はありません。V4 の `/save_data` はデフォルトで deprecated を返し、`plugin.v4_compatible.simulate_save_data: true` で以前の応答を再現できます。
- 1 つのデータベースを 1 つのサービスプロセスで管理します。複数プロセス間でのスナップショットの同期、分散配信、複数インスタンスでの運用には対応していません。

## Docker

インストールスクリプトを使うのがいちばん簡単です。リポジトリの clone、`docker-compose.yml` の作成（シークレット入り、パーミッション 600、Git の管理対象外）、ビルドと起動までを行います。もう一度実行すればアップデートになります。

```sh
curl -fsSL https://raw.githubusercontent.com/kisukri/sleepy-go/main/deploy/install.sh | bash
bash ~/sleepy-go/deploy/install.sh   # アップデート
```

作成される Compose ファイルでは、コンテナを `data/` の所有者として動かし、ポートを `PORT`（デフォルト 9010）に割り当てます。状態とログは次のコマンドで確認できます。

```sh
cd ~/sleepy-go
docker compose ps
docker compose logs --tail=50
```

リポジトリに入っている Compose のサンプルも使えます。

```sh
mkdir -p data
export SLEEPY_UID="$(id -u)"
export SLEEPY_GID="$(id -g)"
export SLEEPY_MAIN_SECRET='長くてランダムなシークレットに置き換えてください'
docker compose -f deploy/compose.yaml up --build -d
```

イメージはデフォルトで uid 65532 として動くので、Compose の UID/GID は `data/` の所有者に合わせてください。データディレクトリに書き込めないときは、起動時にわかりやすいメッセージが出ます。`data/config.*` を置いている場合は環境変数より優先されるので、コンテナで外からのリクエストを受けるなら、設定ファイルで host を `127.0.0.1` にしていないか確認してください。

イメージはマルチステージビルドで作り、実行用のレイヤーは scratch です。中身はプログラムと CA 証明書だけで、タイムゾーンのデータは組み込み済みです。HTTPS プロキシを経由する環境では、ビルド時に CA 証明書のバンドルを渡せます（依存パッケージのダウンロード中だけマウントされ、イメージには残りません）。

```sh
docker build -f deploy/docker/Dockerfile --secret id=proxy_ca,src=/path/to/combined-ca-bundle.pem -t sleepy-go .
```

## テスト

`go test -race ./...` では、SQLite への保存、旧データ構造、部分的な更新、認証とセッション、別サイトからの書き込み防止、プライバシーモード、文言のフィルタリング、組み込みファイル、V4 の応答、SSE（初回送信・変更・ハートビート・切断・HEAD）、同時読み書きに加えて、大きな整数の精度、リクエストボディのタイムアウト、設定の上書き、`using` の互換解析、壊れたデータ行、変化のない書き込み、リバースプロキシ利用時の 403 メッセージ、ログアウト、バージョン付き静的ファイル、Windows クライアントの送信ロジックなどの回帰テストを行います。静的チェックには `go vet ./...` を使い、CI では arm64 のビルド、govulncheck、Docker イメージのビルド、Windows クライアントのビルドも行います。

開発マシンで 1 回だけ計測したところ（Linux amd64、Go 1.27.3、メモリ上の SQLite、トップページにアクセスした後）、シンボルを除いた実行ファイルが約 13.45 MiB、待機中のメモリ使用量（RSS）が約 13.4 MiB、SSE を 20 本つないだ状態で約 14.3 MiB でした。本番環境での負荷試験ではないので、実際のデータ量や同時接続数によって使用量は変わります。
